# /loop-goal — ゴールは宣言ではなく発見

ループを回すときに、**着手時点でゴールを言葉にできること**を前提にしない。ここが緩和したい点そのものなので、前提にすると門番になる。

代わりに、ゴールを毎反復で書き換わる対象として扱い、その書き換えを記録する。書き換えが止まったことが収束の signal で、**そこで初めて**終了判定が書けるようになる。

## この手順が面倒を見る2つの失敗

- **終わりを言葉にできない** — 着手前に「何ができていたら完了か」を書こうとしても書けない。だから、とりあえず回し始めてしまう。
- **やってみて初めて本当の要件が分かる** — 最初に書いたゴールが、数反復後に見ると違っている。書き換えたいが、書き換えたことが記録に残らず、後から「なぜこうなったか」が辿れない。

どちらも「ゴールが不安定であること」が原因ではなく、**不安定さが記録されないこと**が原因。日誌がその一点だけを引き受ける。

## 着手時に書くのは3つだけ

ゴールは要求しない。要求するのはこれだけ。

| 項目 | 中身 | 書けないとき |
|---|---|---|
| **向き** | 何を良くしたいのか。1文 | ここが書けないならループではなく調査。ループを始めない |
| **最初の一手** | 次の1反復で具体的に何をするか | 同上 |
| **予算** | 何反復まで / 何分まで | **必ず書ける。これだけは例外なし** |
| **席** | どのプランが払うか | **同上。予算と同じ理由で例外なし** |
| 暫定ゴール | 今わかる範囲の「終わり」 | `不明` と書く。**それが正しい初期値** |

予算が「必ず書ける」ことが要点。ゴールが書けないことは許すが、無限に回すことは許さない。ゴールの不確かさと停止の保証は別物で、後者はいつでも決められる。

席も同じ形の例外なし。反復のたびに日誌と文脈を読み直すので、**長いループは席のプランをいちばん速く空にする**。どのプランが払うかはゴールと無関係で、着手時にいつでも決まる。数十反復回ることが分かっているなら、始める前に Grok の席へ移す（そのつもりで `cursor-agent` で開き直す）。移せない事情があるなら、各反復の重い読みを `delegate --wait bulk` で渡して、この席は日誌の管理だけを持つ。

## 日誌を作る

`.loop/<slug>.md` に置く。dotfiles の `config/git/ignore` が `.loop/` を無視するので、どのリポジトリでも `.gitignore` を触らずに済む。残したくなったら、そのファイルだけ移動して commit する。

```markdown
# <一言でこのループの名前>

- 向き: <1文>
- 予算: 最大 <N> 反復 / <M> 分
- 席: <claude | cursor-agent (Grok)>
- 暫定ゴール: 不明

## #1
- した: <1行>
- 分かった: <暫定ゴールについて何が分かったか>
- ゴール: <書き換えた新しい暫定ゴール> / unchanged
```

## 各反復の終わりに追記する3行

**これが唯一の強制事項。**反復を1つ終えたら、必ず次を追記してから次の反復に入る。

1. **した** — その反復で実際にやったこと。1行
2. **分かった** — 暫定ゴールについて何が分かったか。「何も分からなかった」も有効な答えで、そう書く
3. **ゴール** — 書き換えた新しい暫定ゴール、または `unchanged`

3 が `unchanged` かどうかだけが、後の判定に使われる。だから正直に書く。書き換えたのに `unchanged` と書くと収束を誤検出し、書き換えていないのに書き換えたと書くと永遠に収束しない。

## 収束と発散、2つの signal

日誌の `ゴール` 行だけを見る。

**`unchanged` が3反復続いた** → 収束。ここで初めて終了判定を書く。

```
判定: <exit 0 で終わるコマンド、または人間が YES/NO で答えられる1問>
```

書けたらそれが停止条件。**まだ書けないなら、`unchanged` が嘘だった**（ゴールが安定したのではなく、ゴールを見ていなかった）。なぜ書けないかを追記して、反復を続ける。

**ゴールが5反復連続で書き換わり続けた** → 中間確認。ここで止めるのではなく、日誌の `ゴール` 行5本をそのまま人間に見せて「この方向で合っているか」を1問だけ聞く。合っていれば続ける。

止めないのが要点。要件が後から分かるループでは、ゴールが5回書き換わるのは正常な進行でもありうるので、これを打ち切り条件にすると緩和したかったものを潰す。区別できるのは人間だけなので、判断はそこに返す。5行を並べれば、どこで曲がったかは説明せずに伝わる。

予算に達したときも同じ。**ゴールが定まらないまま予算を使い切ったことは失敗ではなく結果**で、そのときの暫定ゴールが着手時より具体的なら、それがこのループの成果。日誌をそのまま渡す。

## /loop と組み合わせる

`/loop` に渡すプロンプトに、**日誌のパスを書き込む**。

```
/loop .loop/<slug>.md の手順で1反復進め、末尾に3行追記する
```

コンテキストではなく日誌が状態を持つので、compact されても、`/loop` が再呼び出しされても、herdr の server を再起動しても手順が失われない。反復のたびに日誌を読み直すことが、この形の要点。

## （任意）別モデルにゴールだけ見せる

`ゴール` 行が本当に `unchanged` かどうかは、書いた本人がいちばん判定を誤る。3反復ごとに、日誌の `ゴール` 行だけを別モデルに渡して聞く。

```sh
delegate --wait bulk goal-check "$(sed -n '/^- ゴール/p' .loop/<slug>.md) — この列は収束しているか、していないか。理由を2文で"
```

`delegate` の役割表は `delegate --list`。書いた本人と別のモデルに見せたい。このセッションが Opus なら `bulk`（Grok）で足りる。すでに Grok なら、同じモデルにもう一枚出さない — 日誌の `ゴール` 行をこのセッションで読み直す。`gpt` は逼迫している別ベンダー枠で、2文の判定には使わない。日誌全体ではなく `ゴール` 行だけを渡すのは、作業内容を見せると「頑張ったから収束している」に引きずられるため。
