# メモリ監査

メモリは**書かれた時点の真実**であって現在の状態ではない。放置すると、同じ問いに複数の答えが等しく正しそうな顔で並び、モデルは自信を持って古い方を答える。ハルシネーションの体感が上がったときの第一容疑者はここ。

対象は `~/.claude/projects/<スラグ>/memory/`。`MEMORY.md`（索引・毎ターン全文がコンテキストに載る）と個別ファイル（recall 時のみ載る）で構成される。

## 探すもの

4 つの型に畳める。実リポジトリ 3 つの監査で、見つかった問題はすべてこのどれかだった。

**化石** — 完了したのに「未マージ / 未 PR / レビュー待ち / 未着手」のまま固まった記述。追記専用のファイルで特に湧く。ある repo では未完了を主張する 12 件が**全件すでに解決済み**で、ブランチは削除されていた。「続きをやって」と言われたモデルは、存在しないブランチを前提に計画を立てる。

**二重の現在** — 「現行 / 最新 / 最有力 / 権威版 / 正式版」を名乗る記述が複数生き残る。後継が出たとき、前任からその語を外す操作が漏れる。ある repo では 5 ファイルが同時に「現行の権威版」を名乗っていた。**最も直接的に誤答を生む型**なので最優先で潰す。

**索引ドリフト** — `MEMORY.md` の一行要約と、本文 / `description` のズレ。更新が片方にしか入らない。同一ファイル内で索引が「不採用」・description が「採用方針」と**正反対**を言っていた例がある。

**揮発値** — バージョン・commit 差分・件数・「次にやること」。書いた瞬間から腐る。危ないのは数値そのものより、**その数値を前提に組み立てられた結論**の方。「main は 217 commits 遅れ ∴ 本番にこの機能は無い ∴ ゲートは GREEN」という推論が、実測 65 commits の今も結論だけ生きていた例がある。

## 手順

### 1. 静的検査をかける

```bash
python3 <skill_dir>/scripts/audit_memory.py <memory_dir>
```

出力は**疑いであって結論ではない**。ここで止めずに 2 へ進む。

### 2. 現物で確定させる

スクリプトが出した PR 番号・ブランチ名・バージョンを、`gh pr view` / `git ls-remote` / `git tag` / `package.json` / 実ファイルの存在で照合する。照合コマンドはスクリプトが生成する。

`description` の主張と**本文の最新セクション**も突き合わせる。ファイルが自分自身と矛盾していることが多い。

完了条件: 抽出された未完了主張・「現在」主張・揮発値が**全件**、実測値と紐付いた状態。1 件でも未照合なら次へ進まない。

### 3. 直す

事実の誤りから先に直す。順序は **二重の現在 → 化石 → 索引ドリフト → 揮発値 → 書式**。

### 4. 鮮度を刻む

`MEMORY.md` の冒頭に監査日と、実測した揮発値と、「引用前に現物確認せよ」の一行を置く。次に読むセッションへの申し送りになる。

完了条件: スクリプトを再実行して「二重の現在」が 1 件以下、frontmatter が OK、デッドリンク・孤児が 0。

## 直し方の規律

**`description` を本文より先に直す。** recall の判定に使われる欄なので、ここが間違っていると誤ったファイルが呼び出される。索引の一行より害が大きい。

**古い記述は消さずに死亡宣告する。** 「【YYYY-MM-DD 修正】マージ済み」のように、旧記述と訂正を併記して残す。当時の判断の根拠が追えなくなるのを防ぎつつ、現在の状態を一意にできる。

**揮発値には観測日を添える。** 「2026-08-11 時点で 65 commits」と書けば、数値が古びても嘘にはならない。

**追記専用の巨大ファイルは「不変の設計核」と「時系列ログ」に割る。** 核だけが日常の判断に載り、ログは特定の経緯を追うときだけ開く。98KB・1 行 11,786 字のファイルを 10KB の核と 90KB のアーカイブに割った例がある。

**YAML を壊す文字を知っておく。** 未クォートの `description` に半角スペース + `#` が入ると、そこから先が**コメントとして捨てられる**。日本語で書いていて `（PR #979）` と添えた瞬間に発火する。`#` を含む description は必ず `"` で囲む。実際に 4 件が切断済みだった。

## 予防

決定が変わったときに前任の記述を直す導線が無いのが根本原因。作業側にこう仕込む:

- 版・状態を上げたら、**前版のメモリから「現行 / 最新」の語をその場で外す**
- PR をマージしたら、その PR を「未マージ」と書いているメモリを `grep` して更新する
- メモリを書くときは、`git log` や `gh pr view` で引ける事実ではなく、**引けない事実**（決定の理由・罠・不文律）を書く
